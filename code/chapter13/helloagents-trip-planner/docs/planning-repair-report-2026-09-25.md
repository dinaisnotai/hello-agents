# 北京行程问题修复报告

日期：2026-09-25。目标：修复酒店坐标、混合交通、餐饮候选、门票状态及攻略检索，并解释原因与验证范围。

本轮保留三个查询 Agent、LangGraph、攻略检索和审查。没有预订、扣费、修改历史行程或提交 Git。真实验证只读取本地保存行程并查询地图、Embedding 服务。

## 1. 先理解根因

原链路并不是每一步都没工作，而是不同模块的假设没有对齐：

```text
英文酒店地址解析 → 得到一个坐标但未确认酒店身份
直线距离估计 → 预选公交或步行 → 只查询这一种真实路线
第一个/最后一个景点 → 搜索最近餐饮 → 咖啡厅也被当正餐
景点类别 → 猜票价 → 博物馆和公园被写成 0
整条旅行需求 → 检索五段文字 → 硬编码规则未必执行其建议
```

因此，地图接口成功、Embedding 接口成功、工作流完成，都不能单独证明最终行程合理。

## 2. 酒店定位与选择

### 已确认原因

凯宾斯基保存坐标为 `116.478519,39.954510`；高德按中英文名称找到的北京燕莎中心凯宾斯基饭店 POI 为 `116.464417,39.949163`，地址同为亮马桥路 50 号，相差约 1.34km。原代码直接接受英文名称加地址的地理编码结果，没有进行酒店 POI 匹配。

此外，原酒店候选最多十家；酒店评分使用重点景点的估算通勤，未在日程形成后复核每日首末景点的真实往返交通。

### 修改

- 新增 `hotel_location.py`：从真实住宿 POI 匹配酒店。优先唯一同名；跨语言名称需要唯一住宿候选和地址门牌号匹配。歧义时保留位置未知，不用地址中心点假装已定位。
- 保存 `location_source` 与 `map_poi_id`，供应商房价与地图位置分开追溯。
- LiteAPI 候选上限由 10 扩到 30；保留星级、房态和报价筛选。
- 初步日程形成后，对预筛的最多三家酒店复核各天首末景点往返路线，再依据真实耗时和步行评分。三家是控制接口开销的工程限制，并非全城最优保证。
- 真实路线以坐标、城市和交通方式缓存，修复重算可以复用；不把估算路线缓存成真实路线。

限制：尚未按所有商圈完整分页搜索，也未做酒店与景点组合的全局优化。跨语言匹配仍是保守启发式，不能声称为供应商与地图间的完整身份映射。住宿价格仍可能是沙箱报价。

## 3. 混合交通与出入口

### 已确认原因

原模式用直线距离决定交通方式，对公交步行预估最多约 800m。实际公交可能需要走两三公里，但返回后没有重新比较打车。景区同一个中心坐标还被用于进入和离开。

### 修改

- 新增 `mixed_route_selector.py`，比较公交与驾车候选；直线短距离再加入步行候选。
- 按真实返回的耗时、步行、估算费用选择；预算按人均每日额度影响费用权重，但最终预算仍重新计算，不能保证每次选车都不会超预算。
- 将每日步行额度扣除景区内部估算，再为路线段分配保守额度。该分配是启发式，不是最优路线求解器。
- 有真实路线时，不允许未验证的驾车估算凭“零步行”击败它。
- 公交不再盲取第一条方案，会在供应商返回方案中比较时间与步行。
- 景点支持独立入口和出口坐标；故宫按官方访问方向解析午门、神武门 POI。无法核实入口时仍明确提示。
- 驾车不再被表述成完全不用走路：增加上下车接驳步行未核实标志，结果页和审查明确提示当前步行只包含已计入部分。

限制：没有实现“出租车接地铁”的联程搜索；上下车合法位置、安检与接驳步行还不完整。候选按接口查询时刻获取，并非未来出发时刻的交通预测。

## 4. 餐饮

原代码只查第一个景点旁的午餐、最后一个景点旁的晚餐，并按直线距离选最近地点。因此没有利用住宿区域，且咖啡厅可能充当午餐。

修改后：

- 正餐排除咖啡、饮品、甜品和酒吧等明显不合适候选。
- 排除识别到的馆内、景区附属餐饮，避免在无法确认访问条件时直接安排闭馆后的内部餐厅。
- 午餐围绕游览点出口；晚餐同时搜索最后景点及酒店周边，比较返程绕行和酒店距离。
- 旧计划中的咖啡厅等不合适餐饮不再直接复用。
- 查不到合适餐厅时预留用餐并标记待确认，仍不生成虚构餐厅。

限制：这是候选与位置联动，不是完整的用餐时间窗优化；餐厅营业、菜单、正餐供给和饮食限制尚需确认。没有硬编码必须去三里屯或蓝色港湾。

## 5. 门票、营业时间和预算

原 `_estimate_ticket_price` 把博物馆、公园等直接写为 0，前端还将缺失值显示为 0 元。故宫在实际保存结果中因此为 0 元。

修改后：

- 停止按类别推断免费，增加 `unknown`、`estimate`、`official_reference`、`confirmed_free` 四种状态及来源、说明。
- 结果页展示“待核实”，预算列出尚未计入的景点，检查文案不再把已计价部分未超预算说成费用已完整确认。
- 新增 `visit_facts.py`，提供本次核验的有限官方参考：故宫成人大门票旺季 60 元、淡季 40 元；国博常规入馆免费但需预约。专馆、特展、优惠资格另核。
- 同时修正故宫的季节营业时间、停止入馆时间及访问方向，避免仍沿用类别估计的 18:00 闭馆。
- 这些参考核验于 2026-09-25，当前程序仅在 2026-09-25 至 2026-12-24 的有限窗口使用；超出窗口重新标记未知。该窗口是本项目的复核策略，不是官方承诺价格在期间不变。

来源：[故宫票务](https://www.dpm.org.cn/subject_booking/)、[故宫导览](https://www.dpm.org.cn/Visit.html)、[国博预约](https://pcticket.chnmuseum.cn/museum-en/)。

限制：尚未接入覆盖全国景区的实时票务接口。未知门票不会计成真实免费，但暂未有可靠报价的项目仍不计入数值小计，所以必须同时阅读预算完整性提示。

## 6. RAG 为什么有向量还不好，以及本轮改法

Embedding 实测成功并返回 2048 维向量。原问题包括：本地知识较少且泛化、把整条需求拼成一次查询、检索文件总说明占用名额、检索内容与确定性规则缺少对应关系。

修改后：

- 按游览、住宿、交通、餐饮分别检索，每类最多两条，去重后最多八条，并记录 `retrieval_purpose`；前端可看到用途。
- 排除攻略文件总说明，补充自然风光、故宫出入口、酒店周边晚餐等具体知识段。
- 混合检索独立于自动数值投影，使用关键词与向量排名融合，也允许结构化知识参与证据检索。
- 结构化数据中已过期的硬事实不进入本轮检索候选。
- 真正的行为改变由上述酒店、交通、餐饮和门票代码落实，不声称检索到某句话就等同于已执行。

最终配置：

```dotenv
TRAVEL_KNOWLEDGE_RETRIEVAL_MODE=hybrid
ENABLE_TRAVEL_KNOWLEDGE=false
```

第二个开关仅控制自动把知识数值投影到评分和时长。本轮试开后，有两项原有景点覆盖回归失败，因此没有启用。此前这两个开关耦合，关闭投影也会阻止混合检索；现已解耦。`.env` 只修改这两项，API Key 保留。

这是一条可以在面试讲清楚的取舍：不能仅为了宣称开启知识增强，就接受景点覆盖变差。

“我先通过保存的输入输出复现，发现酒店地址解析偏移约 1.34km，交通选择用的是直线预估，门票又把类别推断成免费。修改时把身份匹配、路线比选、价格状态分别建模，并保留未知值。通过离线回归及一次真实地图重算证明这些环节改变了行为，同时保留闭馆冲突和接驳步行未知提示。RAG 则按决策问题拆分检索；自动数值投影因回归退化没有上线。实现使用 AI 辅助，我需要能解释每条证据、修改依据及验证边界。”

## 10. 追加修复：布局、正餐身份与小幅超时

用户复查发现景点说明被作为列表项的并列内容渲染，窄列中每个汉字换行；晚餐还出现了名称含酒店名的汽车充电站。这说明“名称像饭店”和“地图餐饮服务”都不能证明是可安排的正餐。

- 结果页将景点名称、时间、地址、票务和出入口说明放进同一个纵向内容块，操作按钮保持独立列；手机屏幕下改为内容在上、按钮在下。浏览器实际检查桌面 1440px 与手机 390px 均无横向溢出，标题保持单行高度。
- 餐饮身份新增充电站、加油站、换电站的优先排除；没有可靠餐饮类型的旧餐食不会复用。糕饼店、面包店、西饼店、饮品和咖啡等也不作为正餐。所有新餐食必须来自有位置的地图 POI。
- 酒店附近餐食改用酒店已确认坐标的周边搜索，而不是用酒店名称全文搜索；因此不会把同名建筑或附属设施当作酒店附近餐厅。
- 北京正餐候选对烤鸭、涮肉、炸酱面给予有限距离优先，并避免跨日重复。这个方向参考[北京旅游网美食合集](https://www.visitbeijing.com.cn/article/4N2Q8LkLW5F)，不等于为单个店背书；只有地图名称或类型明确匹配时才标注“本地特色方向”。
- 营业时间修复新增第一优先级：在已于最后入场时间前到达、且超时不超过原停留时长四分之一与 60 分钟上限时，缩短停留以便闭馆前离开；记录原时长、调整后时长和原因。随后才尝试改顺序；仍不可行则保留阻断提示或尝试跨天，不删除景点来掩盖问题。

对故宫的真实局部复查从 14:17–17:17、180 分钟调整为 14:17–16:58、161 分钟。若在 16:20 才抵达，已晚于 16:00 停止入场，程序不会以缩短游览时长掩盖该错误。

## 12. 对话重规划复盘：圆明园分支、审查和 RAG

### 复现的事实

读取“加入圆明园”后的本地会话版本可见：第三天被安排为“圆明园遗址公园-多稼轩”“圆明园遗址公园-西北景区”“圆明园-思永园”。它们都是同一用户请求对应的主园、景区或内部支线，而不应被当成三次独立游览。该版本的晚餐 POI 类型字段为空，却被标记为 `map_poi`，所以旧结果中的汽车充电站没有可供质量门验证的餐饮类型证据。

同时，该会话的 `quality_evaluation` 为空，质量门追踪中的 `reviewer_issues` 也为空。HelloAgents 会在运行时加载自己的提供商配置；本地初始化验证显示实际可使用 DeepSeek 模型。因此仅从保存的计划不能断言这一次完全没有发出 LLM 调用，但可以确定没有任何被接受的 LLM 问题留在计划中。此前的确定性质量门只按 POI ID、直接父 ID 和近距离同名去重，无法识别不同父 ID 的圆明园内部 POI。

### 修复

- 新增“用户请求层”的景点身份：同一条 `must_visit` 同时命中主园、景区和内部景点时，只能占用一个游览名额；这条规则只对用户明确指定的景点生效，不会把普通的相邻景点合并。
- 若高德文本搜索只返回内部支线，程序会使用返回的 `parent_poi_id` 查询 POI 详情并优先选择主园。质量门也加入同样的语义重复检查，即使前面的候选收集出现回归，也会将其标为阻断性 `duplicate_visit`。
- 对该会话做只读验证，质量门已识别到一个语义重复问题；去重后第三天只剩一个圆明园实体，并移除了两项重复支线。使用当前餐饮查询重新计算，该日返回的是具备 `餐饮服务;中餐厅` 类型证据的湘菜午餐和烤鸭晚餐。
- 审查模型若返回未受支持的 `repair_strategy`，旧代码会错误地包装成“通过、无问题”的 LLM 评价。现在已知的历史别名（例如 `swap_weather_sensitive_attractions`）会明确映射为受控的 `SWAP_WITH_INDOOR_CANDIDATE`；其余无效输出会记录为合同错误、被丢弃，并继续使用确定性质量门。无效模型输出不会再替代实际审查。`.env.example` 也说明了标准 OpenAI 兼容配置与 HelloAgents 运行时提供商配置的关系。

### RAG 的实际边界

当前配置为 `TRAVEL_KNOWLEDGE_RETRIEVAL_MODE=hybrid` 与 `ENABLE_TRAVEL_KNOWLEDGE=false`。前者会检索并展示攻略片段，后者禁止把知识库中的分数、时长或偏好自动投影到候选排序。这是此前发现覆盖率回归后的保守配置，因此 RAG 当前只参与说明和可追溯证据，并不改变景点、酒店或路线选择。结果文案现会明确说明这一点，不再把“检索到了攻略”说成“攻略已经影响了规划”。

若要让 RAG 真正参与决策，应先为每个城市补充带 POI 身份、适用条件、来源和过期时间的结构化事实，再以受限的特征投影和回归集验证其是否提高偏好覆盖与可行性；不能让通用攻略文本直接替代地图身份、营业时间或路线计算。

本轮新增 4 项用户请求层身份回归和 1 项 LLM 策略别名回归；最终离线回归为 208 项测试通过。

## 13. 追加修复：午餐后直接晚餐

该问题来自餐点排序规则：午餐固定放在第一处景点后，晚餐固定放在最后一处景点后。当天只有故宫时，排序自然成为“故宫→午餐→晚餐”。原排程没有默认晚餐时段，也没有把抵达晚餐地点后的等待时间表达为休息；利用率又把交通和两顿饭计算在内，因此不会被“单景点且利用率低”的规则发现。

修改后，默认晚餐不早于 17:00；若当天的结束时间和返程仍容得下，较早抵达晚餐地点的时段会写入 `schedule_blocks`，并在结果页展示为“晚餐前休息”。当天仅有一个景点时，晚餐候选改为优先在酒店周边查询，使“午餐后回酒店休息，再用晚餐”有位置依据。若用户明确把每日结束时间设为 18:00 或更早，则不强制延后晚餐，以免为了形式合理而违反可用时段。

质量门会将保存计划中早于 17:00 的下午晚餐标为可修复体验问题；新排程产生的休息块是路线时间推导出的派生数据，不会被误判为质量修复越权。新增两项回归分别覆盖“17:00 后的晚餐和可见休息块”及“旧计划下午晚餐的质量提示”。最终离线回归为 210 项测试通过；前端 `vue-tsc && vite build` 通过，仍保留原有的大 JavaScript chunk 提示。
