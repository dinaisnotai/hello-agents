# 商业化行程助手演进计划

## 当前基线

当前版本采用四 Agent 混合架构：

1. `AttractionSearchAgent` 理解偏好并调用景点 POI 工具。
2. `WeatherQueryAgent` 查询天气并总结天气风险。
3. `HotelAgent` 理解住宿要求并调用酒店 POI 工具。
4. `PlannerAgent` 使用确定性空间规划器生成可执行行程，再由 LLM 结合天气、约束和 RAG 做只读软审查。

距离、交通时间、预算、每日容量和约束报告不交给 LLM 计算。LLM 不可用时，四个 Agent 都能降级到确定性流程。

## 下一阶段目标

让 LLM 从“只读 Reviewer”升级为“行程草案规划者”，但仍不直接控制事实数据和精确计算：

```text
用户需求
  -> LLM 提取结构化旅行意图
  -> 专家 Agent 获取景点、天气、酒店和攻略证据
  -> PlannerAgent 生成每日主题与候选分配草案
  -> SpatialItineraryPlanner 校正距离、顺序、交通和每日容量
  -> ConstraintChecker 检查硬约束
  -> 不满足时执行一次有边界的修复循环
  -> LLM 解释最终行程
```

## 当前真实联调发现

- 四个 Agent 串行执行一次北京一日游约需 107 秒；下一步应并行执行前三个独立 Agent，并记录各阶段 P50/P95。
- 空间规划阶段使用稳定交通估算控制容量，但高德实际路线返回后可能使当天重新超时；需要增加“真实路线回填后的二次容量检查与一次确定性修复”。
- 当前 `daily_distance_km` 汇总了公交等全部路线里程，却被每日步行约束直接使用；需要拆为 `daily_route_distance_km` 与 `daily_walk_distance_km`。
- 首次联调中四个 Agent 均成功使用 LLM，未触发 fallback；仍需补充模型超时、工具失败和非法 JSON 的接口级演练。

## 计划工作包

### P1：结构化需求理解

- 新增 `TravelIntent`：同行人、体力偏好、开始/结束时间、软偏好、硬约束。
- 仅在存在自由文本时调用 LLM 解析；纯表单输入直接映射，避免无意义调用。
- Pydantic 校验失败时保留表单原值，不允许 LLM 覆盖显式选项。

验收：老人、亲子、少走路、不要早起等表达能稳定转换为可检查字段。

### P2：让 RAG 进入规划决策

- 攻略切片增加景点实体、有效日期、信息类型和来源标识。
- 检索预约、闭馆、排队、体力强度、雨天适配等地图 API 缺少的信息。
- RAG 结论必须绑定真实 `source`；无来源信息不能形成硬结论。
- 开放时间、门票和预约信息增加时效性标记，过期证据只作提示。

验收：结果能说明哪条建议来自哪份资料；伪造来源被程序拒绝。

### P3：LLM 行程草案协议

- 新增 `PlanningDraft` 和 `DailyIntent`，只允许 LLM输出每日主题、候选景点 ID、优先级和理由。
- LLM 不输出距离、分钟数、价格和虚构 POI。
- 必须使用专家 Agent 返回的 `poi_id`，未知 ID 自动剔除。

验收：LLM 真正参与每日主题和候选分配，但不能绕过候选集合。

### P4：算法校正与有限修复

- 空间规划器接收 LLM 草案作为软偏好，而非最终结果。
- 继续执行地理聚类、最近邻排序、酒店往返和时间容量检查。
- 约束失败时生成结构化问题，最多让 PlannerAgent 修复一次，防止无限循环。
- 修复后必须重新运行完整硬约束检查。

验收：相同结构化输入保持稳定；每日时长、必去点和避开类型不因 LLM 草案失效。

### P5：实时性与可预订能力

- 接入更完整的开放时间、门票、酒店价格和库存来源。
- 价格、库存和路线均显示数据来源与查询时间。
- 预订动作必须经过用户确认，LLM 不直接提交订单。

验收：展示值与上游响应一致；所有外部写操作都有明确确认步骤。

### P6：评测和可观测性

- 记录每个 Agent 的耗时、工具调用、是否降级、Token 用量和解析失败原因。
- 扩展评测集：远郊、老人、亲子、雨天、闭馆、预算不足、候选不足、服务超时。
- 对比三种模式：纯确定性、当前混合版、LLM 草案 + 算法校正版。

核心指标：

- 硬约束满足率
- 平均每日超时分钟数
- 总路线距离
- 相同输入稳定率
- 无依据事实率
- Agent 降级率
- P50/P95 响应时间
- 单次规划模型成本

## 暂不实施

当前阶段不做以下内容：

- 不让 LLM 独自输出最终可执行行程。
- 不引入复杂 TSP/VRP 优化器。
- 不自动预订酒店、门票或交通。
- 不执行无限多轮 Agent 讨论。
- 不把实时价格和开放时间交给模型记忆回答。

## 推荐实施顺序

`P1 -> P2 -> P3 -> P4 -> P6 -> P5`

先完成可验证的规划闭环和评测，再连接交易与库存能力。
