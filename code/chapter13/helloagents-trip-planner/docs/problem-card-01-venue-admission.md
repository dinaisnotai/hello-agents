# 问题卡 01：错误场所为什么会进入景点候选

## 现象与证据边界

用户曾在北京行程中看到医院和餐厅占用了景点名额。本次检查发现两个可以直接复现的入口漏洞，但没有当时完整的地图响应和调用轨迹，因此不能断言历史问题完全由它们造成。

数据经过：地图搜索 → POI 解析 → 候选过滤 → 身份去重 → 评分 → 每日安排 → 最终检查。

## 根因

1. `amap_service.py` 的 `_parse_pois` 在返回数据缺少类型时，用搜索关键词补上类型。搜索“景点”代表用户想找什么，不代表返回的每个结果都是什么。
2. `venue_policy.py` 的 `venue_kind` 默认返回 `attraction`，把“没有发现排除理由”当成“已有可游览依据”。
3. 原分类把名称和类型混合检查。名称里的“饭店”可能盖过地图给出的“住宿服务”类型。候选收集器还维护了另一套关键词排除规则，容易与统一分类发生冲突。

## 修改

- 地图没有返回类型时保留空值，不用搜索词伪造类型。
- 分类先识别明确的供应商类型；明确的医院、住宿、餐饮、交通等类型不能进入景点候选。
- 明确的博物馆类型可以支持“医院旧址博物馆”作为候选，但不证明它当天开放。
- 名称中的售票处、出入口等仍拦截；笼统“景点”标签不能覆盖名称中的医院信息。
- 未识别的记录返回 `unknown`，入口和最终检查均不把它当作景点。
- 保留明确商场、购物中心等可游览类型，以及已有内部分类和精确别名的兼容性。
- 候选收集器使用统一分类规则，避免另一份关键词列表覆盖其结论。

关键代码：

- `backend/app/services/amap_service.py`：解析时保留缺失类型。
- `backend/app/services/venue_policy.py`：分类优先级及 unknown 默认值。
- `backend/app/agents/trip_planner_agent.py`：评分前过滤。
- `backend/app/services/place_name_service.py`：别名匹配兼容，不让天坛匹配天坛医院。
- `backend/tests/test_venue_admission.py`：地图解析到候选过滤、类型冲突、别名和最终检查回归。

## 验证

新增四个测试方法，包含多个输入子案例。完整后端 unittest 共 186 项通过。运行时仅在测试进程中将 `settings.hotel_api_provider` 设置为 `none`，避免真实酒店报价改变测试预期；没有修改 .env。

首次直接运行时，有两项场所规则兼容性失败，已修复；另三项酒店测试受本地已配置的供应商影响，在隔离真实酒店查询后通过。这里验证的是程序行为，不是线上数据准确率。

## 仍然存在的局限

当前仍使用供应商类型文本、内部标签、名称启发式和少量明确别名，并没有接入完整的地图类型编码映射。错误的供应商类型或模型生成的标签仍可能误导分类。字段未知时保守过滤，也可能漏掉真实但未识别的景点。

场所身份正确不等于可以预约、当天开放或适合该用户。类型来源可信度、缺失真实坐标的处理、最终结果解释，以及未知必去点的澄清流程仍需独立完善。

## 面试时如何解释

“我定位到候选入口把搜索意图误当成场所属性，并默认放行未知类型。修改时保留缺失值、建立类型优先级，并统一入口过滤和最终检查的分类逻辑。用医院、历史博物馆、酒店、购物中心和别名案例验证，防止只修一个名字却误删合法场所。实现使用了 AI 辅助，我通过代码路径和回归结果理解并验证这次修改。”
