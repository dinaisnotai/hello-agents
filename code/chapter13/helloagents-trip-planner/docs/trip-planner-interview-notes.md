# 智能旅行规划助手：面试学习题与参考回答

这是一份基于本仓库实际实现整理的学习材料，不是需要逐字背诵的“标准答案”。回答时先讲结论，再讲具体模块、一次真实问题和取舍；遇到没有实现的能力要明确说“当前没有做”。

## 0. 项目介绍与回答框架

### 1. 用一分钟介绍项目。

**短答：**

这是一个面向多约束出行规划的全栈应用。用户输入城市、日期、预算、节奏、酒店偏好和必去景点后，系统用 LangGraph 编排景点、酒店、天气查询 Agent；然后以高德地图 POI 和路线作为事实来源，通过确定性空间规划器完成分天、排序、交通、餐饮、预算和营业时间校验。最后会经过质量门和有界修复，支持保存会话并通过对话增量重规划。

**展开：**

我把系统分为两层。LLM 和 Agent 擅长理解偏好、决定查询关键词、归纳天气风险和审查体验问题；距离、路线、酒店坐标、营业时间、预算以及硬约束则由地图数据和确定性代码处理。这样可以避免让模型“编造”路线和价格。规划后，如果发现重复景点、非餐饮 POI、超预算、超步行、闭馆或时间轴不合理，会在深拷贝沙箱中尝试有限次数的修复，只有不引入新硬问题才提交。

**可以补充的真实例子：**

我曾发现系统把圆明园内部区域当成三个景点、把充电站当晚餐、把 15 点多安排成晚餐。后来分别增加了 POI 父级/语义身份、场所类型准入和晚餐时段加显式休息块。这说明我不是只调 prompt，而是把失败模式变成可测试规则。

### 2. 为什么把它做成 Agent 项目，而不是普通规则规划器？

**短答：**

旅行需求包含自由文本、偏好解释、天气风险和多类外部信息查询，Agent 适合决定“查什么、怎样解释”；但最终行程不能只由 Agent 生成，所以我将 Agent 限制在查询策略和软审查层。

**展开：**

纯规则系统需要把每一种自然语言偏好和查询策略都硬编码，扩展成本高；纯 LLM 系统又会把未知门票、医院或错误 POI 写进计划。因此本项目让 Agent 调用受限地图工具并输出结构化结果，确定性规划器再根据候选、坐标、时间窗口和预算形成计划。两者分工不同：Agent 提供弹性，算法提供可执行性和可解释性。

### 3. 这个项目有几个 Agent？它们是真正不同的模型吗？

**短答：**

主链路有景点查询、酒店查询、天气查询 3 个专家 Agent，以及 1 个 PlannerAgent。当前它们可以复用同一个 LLM 客户端，核心差异是角色提示词、可用工具和结构化输出合同，不是四个不同模型或四个独立服务。

**展开：**

景点 Agent 输出查询关键词和景点候选方向，酒店 Agent 输出住宿查询方向，天气 Agent 输出风险摘要；PlannerAgent 不直接生成整份自由文本行程，而是先调用确定性规划器，再对结果做只读体验审查。这样的设计便于未来给不同角色配置不同模型、工具权限或成本预算，但当前不夸大为“多模型协作”。

**追问：多 Agent 的价值会不会只是换了 prompt？**

当前最直观的差异确实是 prompt 和工具边界，但更重要的是职责隔离、独立 fallback、结构化输入输出和独立可观测轨迹。比如天气 Agent 失败不会让路线规划失败；景点 Agent 的候选必须经过地图和场所准入，而不是直接被 Planner 信任。

## 1. 编排、状态与降级

### 4. LangGraph 在这个项目里做什么？

**短答：**

LangGraph 负责串联和管理“检索证据 → 三类查询 → 候选扩展 → 确定性规划 → 验证/修复 → 审查”的状态化工作流，而不是代替路线算法。

**展开：**

每个节点读写受类型约束的工作流状态，例如用户请求、候选 POI、天气、酒店、RAG 证据、当前计划和质量结果。这样可以把外部查询、规划和修复拆开，也便于记录节点降级、修复尝试和最终状态。项目还保留 simple/legacy 模式用于故障隔离；当 LLM 或外部服务不可用时，可以使用确定性候选和估算路线完成降级结果。

### 5. 外部 API 或 LLM 失败怎么办？

**短答：**

外部服务失败不会直接让接口崩溃。地图服务、专家 Agent 和 LLM 审查都有 fallback；计划会标明来源和待核实信息，质量门仍然执行。

**展开：**

没有高德 Key 时，系统可以使用本地演示 POI 和路线估算，但不会把估算伪装成真实导航。LLM 初始化或审查失败时，确定性计划和质量门继续执行。门票、营业时间、餐厅类型和酒店报价无法验证时会保留 `unknown` 或 `unconfirmed` 状态，而不是凭空填一个确定答案。

### 6. 为什么不让 LLM 直接输出 JSON 行程，然后前端展示？

**短答：**

因为 JSON 格式正确不等于行程正确。LLM 不适合保证 POI 身份、距离、营业时间、预算和重复景点这些可验证事实。

**展开：**

系统允许 LLM 输出结构化的查询建议或体验问题，但行程对象必须由地图候选和确定性规划器构造。LLM 审查输出还要经过 Pydantic 合同校验和证据落地校验：无法对应到已知天数、候选 POI 或证据来源的问题不会授权修复。这是把“模型建议”与“系统事实”分开的关键。

### 7. 你如何处理 LLM 输出不符合合同？

**短答：**

我先用 Pydantic 校验；对历史上出现过且语义明确的策略别名做显式映射，其余无效结果不采信，继续执行确定性质量门。

**展开：**

真实问题是审查模型曾输出 `swap_weather_sensitive_attractions`，但修复器只认识枚举里的 `SWAP_WITH_INDOOR_CANDIDATE`。旧逻辑错误地把这个合同错误包装成“通过、无问题”，使 LLM 看起来没有作用。现在只映射少量已知别名；未知策略记录合同错误并丢弃，不能被当作审查通过。这比无限宽容地接受自由文本更安全。

## 2. 候选、地图与空间规划

### 8. 一次旅行规划的核心流程是什么？

```text
TripRequest / 对话补丁
  → RAG 证据检索
  → 景点、酒店、天气 Agent 决定查询方向
  → 高德 POI / 天气 / 路线查询与候选过滤
  → POI 身份合并、偏好打分、按区域分天和排序
  → 计算餐饮、交通、预算、营业时间和时间轴
  → 确定性质量门
  → 深拷贝修复候选并重新校验
  → LLM 体验审查与最终结果/风险提示
```

### 9. POI 候选是怎么选的？

**短答：**

先按偏好、经典地标和必去点召回地图 POI，再做场所准入、身份去重、偏好/地标/距离等特征评分，最后由空间规划器根据区域和每日时间容量选点。

**展开：**

必去点有单独召回，首次到访还会补充城市核心地标，避免只召回小众地点。候选先过滤掉用户避开类别和不能游览的场所，再通过 POI metadata 将地图分类转成统一标签。分天时使用坐标聚类和候选增量成本，而不是简单按总分取前 N 个，所以同一片区的景点更可能排到一天。

### 10. 为什么会出现“圆明园被安排三次”？怎么修？

**短答：**

地图供应商可能把主园、入口、分区和内部园林作为不同 POI 返回；仅按 POI ID 或直接父 ID 去重会漏掉多层父子关系。现在对用户显式 `must_visit` 增加语义根身份：命中同一必去景区的主园和内部区域只算一次游览。

**展开：**

候选收集阶段会尝试根据 `parent_poi_id` 查询 POI 详情，优先找到主园；身份解析器仍保留 provider ID、parent ID、名称和坐标的常规去重。即使前置召回回归，质量门也会再次检测“同一用户必去实体”的重复并以 `duplicate_visit` 阻断。这个规则只对用户明确指定的大景区生效，避免误把普通相邻景点合并。

### 11. 如何避免医院、充电站被当成景点或餐厅？

**短答：**

不能只看名称或搜索关键词，必须同时检查地图 provider type 和场所准入策略。景点候选和餐饮候选分别有白名单/排除规则，质量门会再次兜底。

**展开：**

例如“凯宾斯基”可能出现在酒店、餐厅、充电站的名称中，名称匹配无法证明它是正餐。餐厅要求地图类型能证明是餐饮服务，并排除咖啡、饮品、甜品、面包、交通和基础设施；景点候选排除医院、学校、交通设施等。若旧会话里的 `map_poi` 餐食缺少可信 provider type，质量门将其标为需要重新查询，不能继续复用。

### 12. 为什么酒店可能离景点很远？怎么改进？

**短答：**

酒店名称的地理编码可能偏到同名建筑或地址中心点，且直线距离不代表真实通勤。改进方法是先确认酒店 POI 身份和坐标，再用每天首末景点的真实路线复核候选酒店。

**展开：**

系统将酒店供应商报价和地图位置分开保存：报价可来自酒店服务，位置必须由地图住宿 POI 确认。初步排程后，最多对若干酒店候选计算“酒店→首景点”“末景点→酒店”的真实路线，根据通勤时间、步行和档次综合选择。这样不会因为高分酒店名义上豪华，却把每天大量时间耗在往返上。

### 13. 混合交通是怎么做的？为什么不能只看直线距离？

**短答：**

先按路线长度和用户交通偏好选择候选方式，再使用高德真实路径复核；公共交通的步行部分、打车接驳和费用要单独计入。

**展开：**

直线距离不能反映地铁站距离、换乘、景区入口和堵车。路线对象会保存总时长、步行时长、公交地铁时长、分步导航和费用估算。对于“混合交通”，系统优先避免长距离步行；若接驳步行无法由地图完全确认，会显式标注，而不是说总步行已精确满足上限。

### 14. 午饭后直接去晚饭的问题是怎么发现和修复的？

**短答：**

旧规则是第一景点后插午餐、最后景点后插晚餐。当天只有一个故宫时，必然得到“故宫→午饭→晚饭”。现在默认晚餐不早于 17:00，早到晚餐区的时间会生成可见的休息块；单景点日的晚餐优先查酒店周边。

**展开：**

此前利用率把交通和两顿饭都算进去了，所以一个下午没有游览内容的日子也可能看似“利用率高”。我增加了时间轴规则和质量门：早于默认晚餐时段的旧计划会提示“补下午活动或明确安排休息”。新计划如果 15:43 到达酒店附近，则会显示 `15:43–17:00 晚餐前休息`、`17:00–18:00 晚餐`。如果用户明确每日 18:00 前结束，则不会机械推迟晚餐造成超时。

## 3. 约束、质量门与修复

### 15. 什么是硬约束和软质量？

**短答：**

硬约束是不能违反的条件，如必去点、预算、每日结束时间、步行上限、已确认闭馆和安全/场所准入；软质量包括多样性、地标覆盖、偏好匹配、交通舒适度和餐饮体验。

**展开：**

两类问题处理方式不同。硬约束未通过时，计划不能被当作可直接执行结果；软质量不足会给出修复建议或 best-effort 提示。这样不会为了填满一天而打破预算和时间，也不会因为少量软问题直接返回 500。

### 16. 质量门具体检查什么？

**短答：**

它检查场所身份、重复、必去点、每日容量、路线交通、硬约束、预算、已确认闭馆、天气、地标覆盖、多样性、偏好和餐饮时间轴。

**展开：**

质量门输出结构化 `ExperienceEvaluation`，每个问题有 `issue_type`、严重度、天数、证据、修复策略和稳定指纹。质量问题不是一个笼统的分数，因此 RepairController 可以知道该“删重复”“补必去点”“换酒店”“重聚类路线”还是“添加室内备选”。

### 17. 什么是事务式修复？为什么要用深拷贝？

**短答：**

每次修复都在计划深拷贝上执行，重新计算路线、预算和质量；只有目标问题改善、未产生新硬问题、且修改范围符合策略时才提交。这避免“修一个问题把原计划改坏”。

**展开：**

修复器有固定策略枚举，例如删重复、补候选、重选酒店、重聚类、降成本或加天气备选。PlanMutationSandbox 记录修复前后质量、约束、计划差异和提交决定。比如一个天气修复不应同时把其他天的景点重新洗牌；修改范围超出策略允许的 scope 会回滚。每轮修复有上限，当前默认最多 3 次，避免无限循环。

### 18. 如何判断修复“更好”而不是只是不报错？

**短答：**

不是只看最终 `valid`。会比较目标问题是否消失、硬约束是否新增、质量分是否退化、预算/交通/步行是否恶化，以及修复是否越权。

**展开：**

举例：为了减少步行而把必去景点删掉，不能算成功；为了替换一个重复 POI 而新增了另一个超预算路线，也不能提交。系统将这些条件写入 commit decision，并保留回滚原因，便于在结果页或调试日志中解释“为什么这个候选没有被采用”。

### 19. 为什么 LLM 审查不能取代确定性质量门？

**短答：**

LLM 适合发现体验层的问题，但无法作为路线、营业时间、POI 类型和预算的最终权威；它的输出还可能格式错误或引用不存在的候选。

**展开：**

因此 LLM 审查是外部 evaluator，确定性门负责合并和最终执行边界。LLM 提出的问题要落到已知候选、已知日期或证据来源上才能被接受。即便 LLM 不可用，确定性质量门仍可完成硬检查和部分修复。这也是项目在工程上比“一个 Prompt 生成旅游攻略”更可靠的地方。

## 4. RAG、数据和事实边界

### 20. RAG 在这个项目中解决什么问题？

**短答：**

RAG 用于提供城市攻略、游览、住宿、交通和餐饮的可追溯证据，帮助查询 Agent 和最终说明理解偏好与风险；它不替代地图 POI、路线或营业时间事实。

**展开：**

检索会按决策目的拆分，而不是将整段用户需求只搜一次；结果记录来源和用途。Hybrid RAG 结合关键词和 Embedding 召回，能够补充“某区域适合什么体验”一类文本信息。但具体的景点身份、餐厅类型和路径仍必须以地图数据为准。

### 21. 既然做了向量检索，为什么 RAG 看起来没有影响行程？

**短答：**

这是有意识的保守取舍：当前 `ENABLE_TRAVEL_KNOWLEDGE=false`，RAG 会检索并展示证据，但其分数、时长和偏好投影不自动改变候选排序，因为曾在覆盖率回归中造成退化。

**展开：**

“embedding 调通”只证明能找相似文本，不代表可以安全地驱动决策。要让 RAG 直接参与排序，需要为每条知识补充 POI 身份、适用条件、来源、时间有效期和置信度，然后做离线对照评测。面试中主动说明这个限制反而能体现你区分了“检索可用”和“决策可用”。

### 22. 门票和酒店价格为什么经常是待核实？

**短答：**

因为这些是时间敏感的交易事实，不能按“博物馆/公园通常免费”这种类别规则硬猜。项目将价格状态、来源和说明独立建模；未知价格不等同于 0 元。

**展开：**

例如系统为少数有可验证来源的景点保留季节性参考价，其他项目会标记 `unknown`，并在预算中提示未计入项。酒店也是类似：可以展示 LiteAPI 沙箱或供应商报价，但不称为真实可订房价。这个设计牺牲了一点“数字看起来完整”的展示效果，换来了更诚实的预算边界。

### 23. 如何处理数据过期和错误？

**短答：**

所有外部或知识库信息都要带来源、状态和待核实提示；对不能验证的字段保留未知，而不是把旧数据升级为事实。

**展开：**

地图路线缓存按城市、坐标和交通方式区分；酒店报价和位置分别追溯；RAG 文档有来源与用途。营业时间、票价和餐饮菜单都属于可能变化的数据，所以结果页会显示来源状态。生产化时我会进一步加入 TTL、数据版本、过期策略和官方票务/酒店 API 的刷新任务。

## 5. 会话、前端与可观测性

### 24. 对话重规划是怎么实现的？

**短答：**

系统使用 SQLite 持久化原始请求、计划版本和消息。用户发“加入圆明园”后，先把文本解析为受类型约束的请求补丁，再合并到当前请求，通过和首次规划相同的入口重新计算并产生新版本。

**展开：**

计划版本和聊天消息分表保存，因此能查看当前版本与历史版本。这里的关键不是在原 JSON 上随意追加一个 POI，而是重跑候选、分天、路线、质量门和修复；否则必去点改变后容易造成重复、预算和时间冲突。

### 25. 如何让结果可解释、可调试？

**短答：**

计划不仅返回每天的景点，还保留候选分数构成、选择/未选原因、路线分段、质量问题、修复历史、约束报告和运行轨迹。

**展开：**

可观测性对象包含用户需求、候选 POI、组合指标、日程、路线和验证信息。前端展示路线、餐厅来源、门票状态、未满足约束和休息缓冲。这样用户看到“为什么没选八达岭”或“为什么餐厅待核实”时，系统能给出路线、容量或数据来源层面的理由，而不是一句“AI 推荐”。

### 26. 为什么没有 Redis、Kafka 或完整数据库？

**短答：**

当前是课程/作品集规模的同步规划服务，SQLite 已经满足会话、版本历史和本地演示；Kafka、Redis 不是为了“技术栈更大”而加入。

**展开：**

如果进入多用户生产环境，我会将长耗时路线/酒店查询异步化，用队列承接重规划任务；用 Redis 做短期路线缓存、会话缓存和分布式限流；用 PostgreSQL 存用户、计划、版本和审计数据；再把监控指标输出到 Prometheus。现在不引入它们，是因为没有并发量、可靠投递或跨实例缓存的实际需求，加入只会增加部署复杂度。

## 6. 测试、评估与复盘

### 27. 如何测试 Agent 项目？

**短答：**

我把可确定的部分写成离线回归，不依赖真实地图、酒店或模型 Key；测试覆盖 POI 身份、餐厅准入、时间轴、路线、约束、修复提交/回滚和 RAG 回退。当前离线回归为 210 项，前端通过 `vue-tsc && vite build`。

**展开：**

Agent 项目不能只测“接口 200”。例如我为圆明园主园/分区去重、充电站不能作为正餐、下午晚餐必须延后或显示休息、LLM 策略别名规范化、修复越权回滚等问题各自增加回归。外部 API 在单元测试中用替身隔离；真实地图测试可以验证集成，但不能作为稳定回归的唯一依据。

### 28. 210 项测试能说明真实旅行计划一定正确吗？

**短答：**

不能。它说明已编码的规则、回归案例和降级行为没有被这次修改破坏，不代表覆盖所有城市、日期、拥堵、排队、景区临时政策或真实价格。

**展开：**

这也是我会在结果中保留“待核实”的原因。下一步应该建立更多城市、不同节奏、特殊人群、必去点冲突和坏数据样例的评测集，并对真实地图调用做录制回放或定期验收。面试时主动说出评测边界，比把测试数当作准确率更专业。

### 29. 你遇到过最重要的失败案例？学到了什么？

**答法示例：**

最有代表性的三个失败是：圆明园的多个内部 POI 被当作多个景点、充电站被当作晚餐、故宫后午饭直接接 15 点晚餐。它们的共同点是上游数据或局部规则看似合理，但没有被完整用户体验约束约束住。

我不再只改模型提示词，而是在链路上找到最早可验证的位置：候选阶段做 POI 语义身份合并，餐饮阶段检查 provider type，时间轴阶段增加晚餐窗口和休息块，质量门再做兜底。这种做法让我理解到 Agent 工程的重点是把失败模式沉淀为数据合同、规则和回归测试。

### 30. 如果继续迭代，你会优先做什么？

**短答：**

第一是扩充带来源和时间有效期的结构化旅行知识；第二是完善机场/火车到达、行李寄存、打车接驳和门票 API；第三是建立真实城市场景的离线评测与线上反馈闭环。

**展开：**

RAG 目前有检索能力但不应直接干预排序，先补结构化事实和评测更重要。交通方面，需要把飞机/火车到站、机场到酒店、入住退房和行李寄存建成明确时间块，再做多段路线规划。工程方面，生产化后再引入队列、缓存、指标和数据库迁移，而不是一开始堆 Kafka。
