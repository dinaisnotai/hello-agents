# 规划流程简化与问题诊断

当前优先级是让候选身份、每日容量、去重和需求检查稳定工作，同时让 Agent、攻略检索、审查修复和 LangGraph 各自承担清晰且可验证的职责。

## 用户日志暴露的问题

| 现象 | 代码中的原因 | 本次处理 |
| --- | --- | --- |
| 天坛同时进入两天 | 同一区域的逐日填充共用候选列表，当天选中后只在所有天完成后清理 | 每一天过滤已经分配的候选 |
| 文华殿得到整个故宫的高分 | 经典召回取第一个匹配就退出；候选去重偏向评分和长名字，提前丢掉主景区 | 保留匹配结果，统一选择主景区；明确要求文华殿时仍保留子景点 |
| 高分景点被换走，低分专题馆补入 | 初始规划、利用率补点、体验修复和 LLM 审查分别改变结果 | 取消基于利用率的自动补点；LangGraph 统一修复预算，修改必须通过事务式质量门 |
| 轻松行程仍可能拥挤 | 初选按 2 / 3 / 4 个，后续区域分配和补点改用统一 5 个上限 | 区域分组、补点入口一致读取节奏上限 |
| 必去点占满后还额外塞入经典景点 | 经典名额没有扣除必去点占用的容量 | 经典名额受剩余容量限制 |
| 专题馆被当成默认经典推荐 | 北京经典列表包含海关、电影专题馆 | 移出默认经典列表；明确兴趣查询仍可召回 |

日志中八达岭的低总分主要来自距离惩罚。若不是必去点，三天行程跳过远郊长城可以合理；不能把所有知名景点都入选当成质量目标。质量检查通过只意味着现有检查没有阻断项，不代表所有选点都值得推荐。日志未包含完整请求、候选数据与当时地图响应，因此本次是针对同类问题的回归验证，不是对那次请求的完整重放。

## 各能力现在如何起作用

- **攻略检索**：先于三个查询 Agent 执行，提供搜索方向和有来源的城市建议；向量不可用时降级为城市内关键词检索。
- **查询 Agent**：景点与酒店 Agent 生成搜索关键词，天气 Agent 生成基于已验证天气的建议。模型输出不能直接成为 POI、酒店、坐标、价格或天气事实，最终候选重新从地图工具构建。
- **确定性规划器**：负责景区身份、候选评分、分天、路线、预算和硬约束。LangGraph 初稿阶段不会在内部偷偷运行另一套体验修复。
- **LLM 审查**：只能返回约定的问题类型和修复策略。未知引用、未知 POI、错误天数或不支持的策略不会获得修复权限，契约错误会留在结果中。
- **多轮修复**：硬约束修复和体验修复共享工作流轮数预算。每次在深拷贝上执行，只有目标问题改善且没有新增硬约束、重复、交通或步行退化才提交。
- **LangGraph**：统一编排意图、约束、检索、三个查询 Agent、初稿、验证、修复、审查和最终输出；会话重新生成也走同一工作流。
- **删除**：无人调用的旧版质量修复循环及专用评分函数，合计约 500 行；移除前端未引用的地图加载器、截图和 PDF 导出依赖及后端未使用依赖。
- **界面**：首页用旅行需求描述功能；结果页以旅行天数替代攻略引用数量，不再把内部检索机制当成产品卖点。

手动重算保留用户调整的行程，重新计算和检查，不自动恢复被用户移除的内容。

## 验证范围与后续边界

新增回归覆盖同区域拆天去重、三个节奏上限、父子景区召回、缺失必去点报告失败、查询 Agent 事实落地，以及模型编造景点、酒店和天气不能进入行程。已有测试还暴露了模型提供的近似坐标被当成另一座同名景点的问题：现在用附近同名地图记录替换没有 POI ID 的候选。

真实数据仍有局限：部分城市的代表性景点资料较少；缺少地图数据时的本地 POI、酒店和路线是演示或估算；自由文本解析覆盖有限；营业、预约和天气不能仅靠规则保证。审查器只能从已有候选中修复，无法弥补地图服务完全没有返回的数据。

后续以固定真实请求逐条验证必去是否满足、是否重复、一天是否太赶、是否优先代表性景点，再决定需要增加哪项能力。不要继续用单一综合评分或利用率作为自动加点的理由。
